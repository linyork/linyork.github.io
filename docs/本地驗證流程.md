# 本地驗證流程（標準化測試）

每次改完東西，用這套流程確認網站真的還是好的。實測環境：Windows 11 + Docker Desktop 29.4.0。

## 一鍵執行

```bash
./dev-verify.sh
```

會做六件事：啟動 Docker daemon（沒開就自動開）→ 清快取重啟容器 → 檢查建置錯誤 →
檢查所有路由 → 確認最新文章有進列表頁 → 確認開發檔案沒被發布。
全綠會印 `PASS`，任何一項失敗印 `FAIL` 並回傳 exit code 1。

停掉伺服器：

```bash
./dev-verify.sh --stop
```

驗證通過後在瀏覽器開 http://localhost:4000。

## 為什麼腳本一定要「重啟」而不是沿用執行中的容器

這是這個專案最容易踩的坑，實測確認過：

**Jekyll 的檔案監看只會重新產生你改到的那一頁，不會重新產生列表頁。**

實測數據：

| 動作 | 文章自己的頁面 | 首頁 / archive |
|---|---|---|
| 新增一篇文章，靠 watcher | 200 ✅ | 沒出現 ❌ |
| 同上，拿掉 `--incremental` | 200 ✅ | 還是沒出現 ❌ |
| 重啟容器（冷建置） | 200 ✅ | 出現 ✅ |

容器日誌會顯示 `Regenerating: 1 file(s) changed`，看起來有動，但 `_site/index.html`
的 mtime 根本沒變。第一次接手這個專案時，首頁最新只到 2020-04，2026 年的兩篇文章
完全不見 —— 就是 `_site/` 留著 2026-01-04 的舊建置，一直沒被重新產生。

實務判斷：

- **只改文章內文** → watcher 夠用，存檔後重新整理該頁即可。
- **新增／改名／改日期／改標題／改分類標籤，或動 `_config.yml`、`_layouts/`、`_includes/`**
  → 一定要重跑 `./dev-verify.sh`，否則你看到的列表頁是假的。

## 環境事實（實測，非推測）

- 容器映像是 `jekyll/jekyll:4`（內建 Jekyll 4.2.2），但 entrypoint 會依專案 `Gemfile`
  跑 `bundle install`，實際執行的是 **Jekyll 3.10.0**，和 GitHub Pages 一致。
  也就是說本地和正式環境版本是**相同**的，不用擔心版本落差。
- 冷啟動約 25–30 秒（gem 已在映像快取中；首次會更久）。
- 專案的 `start-dev.sh` / `start-dev.bat` 用 `-it` 前景執行，適合人工開著看日誌；
  `dev-verify.sh` 用 `-d` 背景執行，參數其餘完全相同。兩者不能同時佔用 4000 埠。
- 開發設定 `_config_dev.yml` 會開 `show_drafts`，所以 `_drafts/` 的 4 篇範例文章
  在本地會出現在列表頁（首頁 35 筆 = 31 篇正式文章 + 4 篇草稿），線上不會。
- `sitemap.xml` 在本地的網址是 `http://0.0.0.0:4000/...`，因為 `_config_dev.yml`
  把 `url` 清空了。這是開發環境正常現象，不是 bug。

## 根目錄新增 `.md` 檔要記得排除

Jekyll 會把根目錄的 `.md` 當成頁面收錄。實測：新增 `CLAUDE.md` 後它被渲染成
`CLAUDE.html`、進了 `sitemap.xml`、還出現在側邊欄導覽列上。

已在 `_config.yml` 的 `exclude:` 加上 `CLAUDE.md`。**日後在根目錄放任何說明文件，
都要一併加進 `exclude:`**，`dev-verify.sh` 的第 6 項就是在守這件事。

## 手動檢查片段

```bash
docker logs jekyll-blog 2>&1 | tail -20
```

```bash
curl -s http://localhost:4000/sitemap.xml | grep -o '<loc>[^<]*</loc>' | sed 's/<[^>]*>//g'
```

文章網址保留大小寫且中文會被 percent-encode，要測特定文章請從 `sitemap.xml` 複製網址，不要自己猜 slug。
