寫 PHP 的人，大概都在某個時間點問過這個問題：為什麼我在檔案最上面設的那個變數，下一個請求進來就不見了？

然後通常有人跟你說「PHP 就是這樣」，你就接受了，繼續寫你的 code。

但這件事其實就是無狀態設計。而且 PHP 大概是所有語言裡把這件事做得最徹底的一個——徹底到你不用學，它直接逼你面對。

## 一個 request 的一生

nginx 收到請求，丟給 php-fpm，fpm 撿一個閒著的 worker，從你的入口檔開始 include，跑完，把結果吐出去。然後——這是重點——整個記憶體清空。你建的物件、你開的 DB 連線、你算了半天的陣列，全部歸零。下一個請求進來，一切從頭再來一次。

這跟 Java、Node 那種「程式跑起來就一直活著」的模型完全不一樣。人家可以在記憶體裡塞一個 map 當快取，放一整天都沒事。PHP 不行，你放了也是白放。

我剛開始寫的時候覺得這設計很笨。每次都要重新 require、重新連資料庫，不是很浪費嗎？後來才知道這個「笨」有一個很值錢的副作用：你的程式天生就不會累積狀態。沒有記憶體洩漏，跑一個月不用重開，第一百萬個請求跟第一個請求走的路完全一樣。出事的時候你不用先問「是不是跑太久了怪怪的」，這句話在其他語言的除錯現場出現的頻率高得嚇人。

## 然後我們自己把它弄髒了

```php
session_start();
```

這行下去，PHP 就在機器的 `/var/lib/php/sessions/` 底下寫了一個 `sess_xxxxx` 檔案。使用者的登入狀態，從此住在那台機器的硬碟上。

單機的時候完全沒問題，順到你根本不會發現有什麼東西被你放進了不該放的地方。

## 加第二台機器的那天

流量變大，要加機器。架好負載平衡，兩台輪流收請求。上線當天客服開始接電話：使用者說他一直莫名其妙被登出。

原因很無聊。他登入的時候請求打到 A，session 檔寫在 A 的硬碟上。下一個請求輪到 B，B 上面沒有這個檔案，PHP 就當作你沒登入。使用者每點一下就在「登入」跟「沒登入」之間跳來跳去。

我覺得這是大部分人第一次真正「體感」到無狀態是什麼意思的時刻。在那之前它只是個名詞。

## 業界大概就三種解法

**第一種是 sticky session。** 讓負載平衡記住這個人第一次去哪台，之後都送同一台。改個設定就好，五分鐘解決，非常香。

代價是你的水平擴展打了折。流量不會平均，總有幾台特別衰，接到一堆重度使用者。那台機器一重開，綁在上面的人全部登出。要縮容的時候更尷尬，你不太敢關機器，因為上面「住」著人。

能動，但它是把問題延後，不是解決。

**第二種是把 session 搬去 Redis。** PHP 這邊改 `php.ini` 的 `session.save_handler`，或者你用 Laravel 就是改 `SESSION_DRIVER`，程式碼一行都不用動。

我一直覺得這件事很漂亮，因為它反過來證明了：`$_SESSION` 這個介面本來就跟「存在哪裡」無關，是我們一直很自然地把它跟本機檔案綁在一起而已。改完之後任何一台都查得到同一份 session，機器隨便加隨便砍。

大部分公司停在這裡。說真的，這對九成的系統就是正確答案。

**第三種是 JWT。** 連查都不用查了，把「你是誰」直接簽在 token 裡，每個請求自己帶著跑，伺服器驗個簽章就知道。

聽起來最乾淨，但它有個很痛的地方：簽出去就收不回來。使用者改了密碼、帳號被停權、權限被降級，那張還在有效期內的 token 照樣暢行無阻。你要做即時撤銷，就得建一張黑名單，然後每個請求都去查那張黑名單——恭喜，你又變回有狀態了，只是繞了一大圈還多背一個 token。

所以我的看法是，JWT 適合服務對服務、短效期、或是你本來就能接受「最多晚個十五分鐘生效」的場景。拿來當一般網站的登入態，多半是把簡單的事情做複雜。

## 講到底就一句話

無狀態不是「系統沒有狀態」。使用者是誰、購物車裡有什麼、訂單走到哪一步，這些狀態一定存在，也不可能消失。

無狀態設計真正在講的是：**狀態不要放在正在處理請求的那台機器上。**

搬去 Redis、搬去資料庫、搬去 S3、甚至搬進請求本身，都可以。重點是跑你程式的那台機器必須是可拋棄的。它就是一個純粹的計算單元：請求進來、算、吐出去、忘掉。

## session 不是唯一的地雷

大家講無狀態只想到登入，但上線之後真正咬你的常常是別的東西：

**上傳的檔案存在 `public/uploads`。** 使用者傳了張大頭照存進 A，下次頁面從 B 出，圖直接破掉。這個不丟 S3 或掛共用儲存是躲不掉的。

**檔案快取。** cache driver 用 file，你清了一台的快取，另一台還是舊的。這種 bug 很容易讓人懷疑人生，因為你「明明清了」。

**log 寫本機。** 機器被砍掉，log 跟著陪葬。等你要查問題的時候，現場已經沒了。

**排程裝在某一台。** 只裝一台，那台掛了就沒人跑對帳；兩台都裝，帳單寄兩份、報表跑兩次。這種問題最難查，因為它平常真的不會發生。

**記憶體裡的計數器。** 像 rate limit 寫「一分鐘只能打十次」，計數如果放在單機記憶體，你有三台就等於實際放行三十次。

這些全部是同一個病：東西存在了不該存的地方。

## 順帶一提，LLM 也是這樣

最近開始碰 AI 的東西，發現 LLM 的 API 根本是同一套邏輯。

你呼叫一次，模型算完就結束，它完全不記得你上一句講了什麼。跟 php-fpm 那個 worker 一模一樣，跑完就清空。

那 ChatGPT 為什麼記得住？因為每次送請求的時候，是把整段對話歷史重新塞一次進去。狀態不在模型身上，在你的請求裡——這不就是 JWT 那招，狀態自己帶著走。

代價當然也一樣：對話越長，每次要傳的東西越多，越慢也越貴。所以才會有 prompt caching 這種東西來補償，本質上跟我們在應用前面擺一層快取是同一件事。

搞懂 HTTP request 的無狀態之後，這些看起來很新的東西，其實都是舊朋友換件衣服而已。
